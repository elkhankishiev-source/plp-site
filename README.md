# Property Library Phuket — сайт

Живёт на **https://property-library.com** (GitHub Pages, ветка `main`).
Публикация: любой `git push` в `main` выкатывает сайт за 1–2 минуты.

Стек намеренно простой: статические HTML-файлы плюс несколько сборочных
скриптов на Node. Никакой сборки фронтенда, npm-зависимостей и рантайма —
что лежит в репозитории, то и отдаётся браузеру.

---

## Главное правило

**Правится только `index.html`.** Остальные страницы — `buy.html`, `rent.html`,
`management.html`, `add-property.html`, `districts/*`, `guide/*` — **собираются
из него скриптами**. Если поправить их напрямую, правка исчезнет при следующей
сборке.

Исключения, которые правятся руками: `owner.html` (личный кабинет),
`rules.html`, `terms.html`, `privacy.html`, `admin.html`.

---

## Как внести правку

```bash
git clone https://github.com/elkhankishiev-source/plp-site.git
cd plp-site

# 1. правим index.html

# 2. пересобираем всё, что из него растёт
node build/gen.mjs          # каталог объектов из базы + страницы объектов + sitemap
node build/mkpages.mjs      # buy.html, rent.html
node build/mkdistricts.mjs  # districts/*.html — 8 районов
node build/mkextra.mjs      # management.html + guide/*.html
node build/addprop.mjs      # add-property.html

# 3. проверяем, что скрипты на странице целы (частая ошибка)
python3 -c "
import re,io
s=io.open('index.html',encoding='utf-8').read()
js=''.join(m.group(1) for m in re.finditer(r'<script(?![^>]*(?:src=|ld\+json))[^>]*>(.*?)</script>',s,re.S))
io.open('/tmp/i.js','w',encoding='utf-8').write(js)"
node --check /tmp/i.js

# 4. публикуем
git add -A && git commit -m "что сделано" && git push
```

Порядок скриптов важен: `gen.mjs` первым, он обновляет каталог в `index.html`,
а остальные берут уже обновлённый файл.

---

## Откуда берутся объекты

Каталог не хранится в коде. `build/gen.mjs` ходит в **Supabase**, таблица
`objects`, и вставляет данные прямо в `index.html` как массивы `PL.PROPERTIES`
(продажа) и `PL.RENTALS` (аренда).

Значит: **чтобы изменить объект, правьте базу, а не HTML.** Потом
`node build/gen.mjs` — и правка на сайте.

Ключи Supabase скрипт берёт из окружения. Без них он не запустится — это
намеренно, чтобы случайно не собрать сайт с пустым каталогом.

Страницы `object/*.html` создаются только для **продажных** объектов.
У арендных своей страницы нет специально: туда однажды утекли имя
собственника и номер квартиры. Их карточки открываются окном на месте.

## Точность координат

У каждого объекта есть поле `coord_source`:

- `verified` — точка сверена по каталогам проектов, ей верим;
- `exact` — задана в ссылке, но не проверена;
- `approx` — приблизительная, на карте рисуется **пунктиром**, в карточке
  подписано «расположение примерное».

Ставить точки удобнее всего мышкой: личный кабинет → раздел «Точки на карте»
(виден только сотруднику). Клик по крыше на снимке со спутника — точка
сохраняется как `verified`.

## Что где лежит

```
index.html            единственный источник разметки и стилей
owner.html            личный кабинет собственника (правится руками)
rules/terms/privacy   юридические страницы (правятся руками)
build/gen.mjs         каталог из Supabase, страницы объектов, sitemap
build/mkpages.mjs     buy.html и rent.html — каталог сеткой с картой
build/mkdistricts.mjs 8 страниц районов
build/mkextra.mjs     management.html и гайды (тексты в build/faq.json)
build/addprop.mjs     add-property.html — пошаговая форма приёма объекта
img/                  картинки, включая img/brand/ — логотипы
CNAME                 привязка домена, не удалять
```

## Живые части

Сайт статический, но общается с внешними сервисами:

| Что | Куда стучится |
|---|---|
| ИИ-консультант в углу | вебхук `site-chat` в n8n |
| Формы заявок | вебхук `site-lead` в n8n → amoCRM |
| Личный кабинет | вебхук `uk-owner` в n8n → Supabase |
| Приём объекта с фото | файлы в Supabase Storage, заявка в `uk-owner` |
| Карта | OpenFreeMap (векторная) и Esri (спутник), оба без ключа |

Ключи вебхуков вшиты в HTML — они публичные и ограничены на стороне n8n
по частоте и белым спискам. Секретов в репозитории нет и быть не должно.

## Чего не делать

- Не править собранные страницы напрямую — затрутся.
- Не удалять `CNAME` — отвалится домен.
- Не добавлять npm-зависимости и сборщики: сайт держится на том, что его
  можно открыть файлом и он работает.
- Не вставлять секреты в HTML.
- Не хостить фотографии объектов в репозитории — они живут в Supabase
  Storage и на Google Drive застройщиков.

## База людей: один человек — один ID

У каждого человека свой номер вида `PLP-003816`. Он выдаётся один раз и не
меняется. Номеров и каналов у человека может быть сколько угодно — все ведут
в одну карточку. Приход в разное время в разные воронки — это его хронология,
а не дубли.

Что лежит под ID: контакты, сделки всех воронок, факты из amoCRM и разговоров,
объекты, задачи, файлы, деньги, лента событий. Смотреть — кабинет, раздел
«Люди» (нужно право `can_see_all_clients`).

**Кабинет не выдаётся всем, кто оставил номер.** Холодному система откажет
сама, остальным решает менеджер. Заявка на продажу или управление заводит ID
и ставит отметку «просит доступ», но не открывает его.

### Перенести переписку в карточку

Старую переписку из WhatsApp система забрать не может: OpenClaw хранит только
ключи сессии и видит лишь новые сообщения, а архив живёт на телефоне. Поэтому:

```bash
# WhatsApp → чат → Экспорт чата → Без медиафайлов → сохранить .txt
export PLP_WEBHOOK_KEY=...
python3 build/wa_history.py ~/Downloads/chat.txt PLP-003816 --dry   # посмотреть
python3 build/wa_history.py ~/Downloads/chat.txt PLP-003816         # залить
```

Даты сохраняются исходные: разговор 2023 года ляжет в ленту 2023 годом.
